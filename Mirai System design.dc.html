3 · IDENTITY, AUTHZ & CONSENT — THE QR IDENTIFIES; AUTH DECIDES
AuthN service
Patients: OTP, passkeys, ABHA federation · Doctors: org IdP (OIDC/SAML per tenant) + MFA · session mgmt · device binding
QR token service
Issues opaque, short-lived rotating tokens · no PHI in QR · expiry, revocation, session binding, rate limits, anti-replay
Policy engine (AuthZ)
RBAC (role) + ABAC (tenant, org, specialty) + consent grants · category-level rules (mental health, sensitive) · emergency break-glass policy · decision logs
Tenant directory
Tenant registry: tier, region, IdP config, feature flags, branding · org & facility hierarchy · practitioner registry (HPR-ready)
▼ authenticated + authorized requests only
4 · CORE SERVICES — stateless, tenant-aware, horizontally scalableevery read/write carries tenant_id + actor + purpose
Patient identity & registry
Global Mirai Patient ID (cross-tenant) · demographic golden record · external-ID mapping per tenant · probabilistic matching, ambiguous → manual resolution · family/guardian links
Medical records
Timeline events, diagnoses, prescriptions, hospitalizations · FHIR-aligned internal model · versioning + provenance (source system, ids, timestamps) · report lifecycle (ORDERED→FINAL→PUBLISHED)
Consent & access
Grants: {grantee, categories, duration, purpose} · request/approve/deny/revoke · auto-expiry · emergency access records · patient-visible access log
Documents
Upload/download via pre-signed URLs · malware scan pipeline · metadata + linkage to events · format support (PDF, DICOM, images)
AI summary service
Patient-friendly + clinical briefs · ask-the-record Q&A · RAG over the authorized slice only · pluggable provider gateway (Azure OpenAI, Bedrock, Vertex, self-hosted) routed per tenant · guardrails, citations, claim-verification · no cross-tenant training
Search
Patient lookup (name, ID, phone, DOB) · permission-trimmed results (identity only until consent check) · per-tenant index partitions
Notifications
Push / SMS / email · templates without PHI · consent requests, report-ready, access alerts, follow-up reminders · per-tenant + per-user preferences
Audit service
Append-only, hash-chained · every view/write/grant/QR scan/break-glass · {actor, role, tenant, patient, action, resource, method, result, session} · tamper-evident, per-tenant export
Event bus
Topics partitioned by tenant_id: report.finalized · record.created · consent.granted/revoked · access.viewed · integration.failed · notification.requested · outbox pattern from services · consumers are idempotent · per-tenant ordering keys
▲▼ async events both ways
5 · INTEGRATION LAYER — hospitals never write to core storesone logical pipeline, per-tenant connectors & credentials
Protocol adapters
REST · FHIR R4 · HL7 v2 · webhooks · SFTP/file drop (legacy) · scheduled sync · adapters plug in without touching the core model
Processing pipeline
Authenticate source→ Validate schema→ Resolve identity→ Map / normalize→ Dedupe→ Persist + provenance→ Publication policy→ Notify
States: RECEIVED → VALIDATING → PROCESSED | REJECTED | RETRYING → FAILED → DEAD_LETTER · idempotency keys = {tenant, source_system, source_record_id, version}
Error handling
Retry with backoff · DLQ per tenant · admin error queue UI · ambiguous identity → human resolution, never auto-attach · nothing silently dropped
▼ all persistence through tenant-aware data access layer (repository enforces tenant_id — no raw cross-tenant queries)
6 · DATA LAYER — isolation by tier, encrypted per tenantenvelope encryption: per-tenant data keys wrapped by KMS master keys
Clinical DB (Postgres)
Pooled: shared tables + tenant_id + row-level security · Siloed: schema-per-tenant · Dedicated: DB/cluster-per-tenant · partitioned by tenant
Identity registry DB
Global patient identities + per-tenant external-ID crosswalk · strict service-only access
Object storage
Documents/DICOM · per-tenant prefix or bucket · pre-signed URLs · lifecycle + legal hold
Search index
Per-tenant partitions/aliases · rebuilt from source of truth · no PHI beyond indexed fields
Audit store (WORM)
Append-only, immutable retention · hash chain anchored daily · separate credentials from app DBs
Cache / queues
Redis: sessions, QR token state, rate counters — keys namespaced by tenant · TTL-bound, no PHI
CONTROL PLANE (shared, no PHI)
Tenant provisioning — create tenant → pick tier & region → provision schema/DB, storage prefix, KMS key, IdP config, subdomain, quotas · automated, idempotent

Plans & metering — per-tenant usage (API calls, storage, seats), feature flags, billing hooks

Config & branding — publication rules, notification prefs, report-type policies, logo/locale per tenant

Lifecycle — suspend, export (patient-portable data out), offboard with secure deletion & retention holds
SECURITY & COMPLIANCE (cross-cutting)
TLS 1.3 in transit · AES-256 at rest · per-tenant envelope keys, rotation · secrets manager (integration creds never exposed) · signed tenant context, defense-in-depth tenant checks at gateway, service and DB (RLS) layers · malware scanning on uploads · pen-testing & SAST/DAST in CI · DPDP (India), HIPAA, GDPR postures via regional cells · data residency pinned per tenant region
OBSERVABILITY
Structured logs, metrics, traces — all tagged tenant_id · per-tenant dashboards & SLOs (QR-to-patient p95 < 500 ms, overview load < 1 s) · noisy-neighbor detection tied to quotas · integration lag & DLQ depth alerts to tenant admins
RELIABILITY & DR
Multi-AZ by default · regional cells (in-region failover keeps residency) · PITR backups per tenant DB/schema · restore drills · RPO ≤ 5 min, RTO ≤ 1 h for clinical reads · read replicas for heavy patient-360 queries · graceful degradation: QR + emergency card served from cache if core degraded
WHY PATIENTS SPAN TENANTS
Patient identity is a global platform entity; clinical records are tenant-owned with provenance. The patient's consolidated timeline is a consented, read-time composition across tenants — this is what makes cross-hospital history possible without hospitals sharing databases.
TENANCY TIERS — same code, different isolation
PooledCLINICS · STARTER
Shared DB + tenant_id column + Postgres row-level security · shared compute · per-tenant encryption keys still apply · cheapest, fastest onboarding
SiloedHOSPITALS · STANDARD
Schema-per-tenant on shared clusters · dedicated search partition & storage bucket · optional dedicated queue consumers · balances cost and blast-radius
DedicatedNETWORKS · ENTERPRISE / GOV
Own DB cluster (or full cell) · pinned region for residency · dedicated KMS keys, optional BYOK · custom SLOs · required for national-platform deployments
KEY FLOW A — QR CONSULT (sync)
Doctor scans QR→ Gateway: tenant + rate + nonce→ QR token → patient id→ Policy: role + consent + categories→ Compose 360° (authorized slice)→ AI brief→ Audit + patient alert
KEY FLOW B — LAB REPORT SYNC (async)
LIS finalizes report→ Integration gateway (tenant creds)→ Pipeline: validate → resolve → normalize→ Persist + provenance→ Publication policy→ event: report.finalized→ Notify patient · audit
MULTI-TENANCY INVARIANTS
1 · tenant_id derived server-side, never from client input
2 · Every query passes through the tenant-aware repository; RLS is the backstop
3 · Per-tenant encryption keys — a leaked key exposes one tenant only
4 · Quotas & rate limits per tenant — no noisy neighbors
5 · Events, indexes, caches, DLQs all namespaced by tenant
6 · Cross-tenant reads exist ONLY via patient-consented composition, always audited
7 · Offboarding exports then provably deletes — audit retained per law
